## 2. 一期范围与边界

后端需要覆盖：

1. M1：登录、考试、类目、题目 CRUD、客观题作答、错题本、统计。
2. M2：AI 文本导入、解析、校对确认、去重、类目归并、导入任务进度。
3. M3：简答题 AI 判分、采分点反馈、超时降级、申诉翻转、统计性能优化。

一期不包含：

- 真实邮件发送和邮箱验证

- 算法题和代码题
- AI 变式题和自动组卷

- 练习进度跨页面或跨设备恢复
- 题目分享、社区、排行榜
- 移动端原生应用

## 7. LLM Provider 抽象

### 7.1 Provider 接口

```ts
interface LLMProvider {
  generateStructured<T>(input: {
    prompt: string;
    schema: ZodSchema<T>;
    signal?: AbortSignal;
    metadata?: Record<string, unknown>;
  }): Promise<T>;
}
```

Provider 层统一处理：

- 超时
- 结构化输出
- Schema 校验
- 失败重试
- token 统计
- prompt 版本
- 模型名称和供应商名称

一期实现 `DeepSeekProvider`。后续新增其他供应商时，只新增 Provider，不修改业务层。

### 7.2 环境变量

```text
LLM_PROVIDER=deepseek
LLM_MODEL=deepseek-chat
LLM_TOKEN_ENCRYPTION_KEY=<32 字节随机串，加密用户 Key 的主密钥，必填>
DEEPSEEK_API_KEY=<仅测试环境 mock 使用，生产留空>
```

凭证解析优先级：当前用户的加密 Key > 无。生产不使用全局 Key；未配置用户 Key 时 AI 接口直接返回错误码，不静默回退。

## 8. AI 导入处理链

0. **入口密钥门禁**：创建任务前同步校验当前用户 Key，未配置返回 `LLM_KEY_NOT_CONFIGURED`、无效返回 `LLM_KEY_INVALID`，均不创建 job，前端即时弹配置引导框。
1. 前端提交原始文本，创建 `import_jobs`，状态为 `queued`。
2. worker 将文本按约 3000 字分块，并发处理 2 到 3 块。
3. 每块携带上一块最后一题的上下文。
4. DeepSeek 返回结构化题目数组。
5. Schema 校验失败时回灌错误并重试，最多两次。
6. 规则校验题型、选项、答案、空位和简答内容。
7. 根据 `stem_hash` 去重。
8. 将已有类目列表塞入 prompt，完成类目归并。
9. 单次导入最多 50 题，超过时提示分批。
10. 解析完成后状态变为 `ready`，由用户校对；`result_json` 中每题带 `confidence` 与 `duplicate` 标记。
11. 用户点击确认导入后调用 `POST /api/imports/:id/confirm`，才批量写入 `questions`。
12. 任务状态流转 `queued → processing → ready → confirmed`，失败为 `failed` 并可经 `POST /api/imports/:id/retry` 重放。

前端通过 `GET /api/imports/:id` 每 1.5 秒轮询一次，显示已解析分段和题目数量。状态机、进度与结果字段定义见[后端技术实现文档.md](./后端技术实现文档.md)第 4.5、6.8 节。

## 9. 简答判分

### 9.1 处理流程

1. 答案为空或少于 5 字时直接判错，不调用 LLM，不校验 Key。
2. 按 `hash(题干 + 用户答案)` 查缓存，命中则复用结果，不重复扣费，不校验 Key。
3. **密钥门禁**：命中正常判分分支时，调用 LLM 前同步校验当前用户 Key；未配置返回 `LLM_KEY_NOT_CONFIGURED` 且不写 attempt，无效返回 `LLM_KEY_INVALID`。
4. 构造题干、参考答案和采分点 rubric。
5. DeepSeek 一次调用返回 JSON，用 Zod 校验分数、命中点、遗漏点、点评和是否正确。
6. 落库 `attempts`（只增不改）；10 秒未返回则写 `is_correct = null` 的流水并返回待自评态。
7. 前端显示正确或错误、命中点、遗漏点、点评和申诉按钮。

判分涉及的五种状态（待判定 / 直接判错 / AI 判定中 / 降级自评 / 判定完成 / 已翻转）及其流转条件见[后端技术实现文档.md](./后端技术实现文档.md)第 4.4 节。

### 9.2 过关规则

同时满足以下两个条件才判定过关：

- `score >= 60`
- 采分点覆盖率 `>= 0.6`

客观题过关口径为"存在 `is_correct = true` 的流水"；错题本的待订正 / 已订正由"是否存在错误流水 + 最新一条有效流水的判定结果"派生，与是否过关是两个独立维度。完整状态机见[后端技术实现文档.md](./后端技术实现文档.md)第 4.2、4.3 节。

### 9.3 容错与成本

- 按 `hash(题干 + 用户答案)` 缓存结果。
- 10 秒未返回时降级为自评，写一条 `is_correct = null` 的流水，由用户自评补判。
- 用户可自评 / 申诉翻转结果：调用 `POST /api/attempts/:id/override` **新增一条流水**并置 `overridden = true`、`original_attempt_id` 指向原记录，原始 AI 判定保留用于调 prompt，**不修改原流水**。
- `is_correct IS NULL` 的流水不计入错误率分母。
- 统计日均调用量和 token 使用量。

## 12. 风险与处理

| 风险 | 处理 |
| --- | --- |
| DeepSeek JSON 不稳定 | Provider 层统一 Schema 校验和重试 |
| 长文本解析不完整 | 分块加跨块上下文 |
| 简答误判 | 申诉翻转并保留原始样本 |
| 统计 N+1 | 使用 `category_stats` 异步重算 |
| 重复导入造成重复题目 | 使用 `stem_hash` 去重 |
| 任务服务重启后卡住 | 启动时把 `processing` 任务恢复为 `queued` |
| 模型成本失控 | 限制单次导入 50 题，记录 token 使用量；用户自带 Key 后成本归用户 |
| 用户数据越权 | 所有查询强制带 `user_id`，并补数据隔离测试 |
| LLM Key 泄露 | AES-256-GCM 加密存储，主密钥走环境变量；响应 / 日志 / 前端存储均不含明文 |
| 未配置 Key 时请求卡住或任务假失败 | 入口同步门禁返回专用错误码，不建任务、不写流水 |
| 用户 Key 失效 / 额度耗尽 | Provider 校验失败返回 `LLM_KEY_INVALID`，提示重新配置，不回退全局 Key |

## 15. 交付给前端的契约约束

- 所有业务接口必须返回可供前端区分的错误码和错误消息，统一结构为 `{ statusCode, code, message, details, requestId }`，错误码表见详细设计文档第 5.2 节。
- 所有业务接口都必须验证用户身份，并按 `user_id` 过滤数据。
- 请求与响应字段统一 camelCase，与前端 `apps/web/src/types.ts` 现有对象名、字段名保持一致，后端返回可为前端类型的超集。
- 导入任务必须返回稳定状态和进度字段（含 `progressJson`、`resultJson`、`confidence`、`duplicate`）。
- 简答判分必须返回分数、采分点、遗漏点、点评和最终判定；`attempts.isCorrect` 需允许 `null`（待自评）。
- 题单接口 `GET /api/questions` 需附带 `answerState`（`passed` / `wrongCount` / `answerCount`），避免前端 N+1 请求。
- `AuthUser.llmConfig` 改为 `configured` + `apiTokenMasked`，不返回明文 Key；提交新 Key 用单独字段。
- AI 接口必须返回 `LLM_KEY_NOT_CONFIGURED` / `LLM_KEY_INVALID`，并在 `details` 中带 `feature` 与 `settingsPath`，供前端弹出配置引导框。
- 题目类型、导入状态和判分结果类型以后端 schema 为单一来源，前端按接口契约对应维护（`packages/shared` 已移除）。
